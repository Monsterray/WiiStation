# DuckStation achievements implementation: WiiStation integration reference

Researched 2026-10-10. All DuckStation links below are pinned to commit `cd024df237d46faa4c65574b101261b31267e2fd` (current master when inspected). Source text was fetched read-only into `/tmp/wiistation-duckstation-ra`; no emulator executable ran and no emulator source changed. ## Client ownership, frame timing, and memory

`CreateClient` supplies memory/server callbacks to `rc_client_create`, installs the event handler, obtains rcheevos's user-agent clause, and appends it to the emulator user agent. It initializes hardcore off and applies unofficial, spectator, and encore settings. It explicitly permits background memory reads. That choice belongs to its threading architecture; it is not a requirement that WiiStation enable this option. [client creation, lines 579–628](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L579-L628).

`System::FrameDone` polls HTTP completions and calls `Achievements::FrameUpdate` once per emulated frame (excluding GPU dump replay). The wrapper then calls `rc_client_do_frame` and updates rich presence. Paused/idle processing polls HTTP and calls `rc_client_idle` instead. Thus frame evaluation follows CPU emulation, not host screen presentations or frame skips. WiiStation should choose one shared emulated-frame boundary in its counters code and continue completion/idle processing in its menus. [frame end, lines 2135–2153](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/system.cpp#L2135-L2153), [frame/idle wrapper, lines 942–960](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L942-L960), [core idle, lines 810–820](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/core.cpp#L810-L820).

Its RA memory space consists of 2 MiB main RAM followed by 1 KiB scratchpad. `ClientReadMemory` returns raw bytes, with an overflow-safe total-range check and selection of RAM or scratchpad. No BIOS or VRAM is exposed. WiiStation's big-endian host must still return the original guest byte ordering from `psxM`/scratchpad, without swapping each returned word. Independently test invalid addresses and requests crossing the RAM/scratchpad boundary: the inspected callback selects one backing buffer based on the starting address, so it is not a substitute for a complete WiiStation bounds design. [map constants, lines 101–104](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L101-L104), [callback, lines 839–864](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L839-L864).

The public interface requires the achievements mutex for access from another thread and defines the overlay lock order. Frame evaluation and server response callbacks take the main mutex. Waiting for owner-tagged HTTP requests can release/reacquire that mutex, avoiding a completion callback deadlock. WiiStation can simplify this with all client mutation/completion dispatch on its emulation thread and short-lived UI snapshots. [lock contract, lines 78–83](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.h#L78-L83), [callbacks/wait, lines 866–960](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L866-L960).

## Canonical identity and disc changes

DuckStation keeps its ordinary game-database identity separate from the achievements hash. It opens track 1 through `IsoReader`, finds the boot executable via `SYSTEM.CNF` (falling back to `PSX.EXE`), removes the `cdrom:` prefix, leading separators, and file-version suffix, and reads that file through its image abstraction. Its RA hash is MD5 of the executable-name bytes followed by executable content, capped at the smaller of declared PS-EXE payload size plus 2048-byte header and actual file size. It validates the PS-EXE header first. A serial or whole-image hash does not replace this calculation. WiiStation should use upstream PS1 hashing and its existing sector reader, with canonical fixture tests; DuckStation's rejection of invalid headers is an implementation detail rather than proof of every upstream fallback rule. [separate identities, lines 674–737](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/system.cpp#L674-L737), [boot name, lines 753–887](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/system.cpp#L753-L887), [MD5, lines 902–925](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/system.cpp#L902-L925).

`SetGameHash` ignores identical hashes, stores identity while inactive or before system start, aborts a previous asynchronous game request, and otherwise calls `rc_client_begin_change_media_from_hash`. It records that a later system reset should reload the game rather than continue treating it as a disc swap. The observed `_from_hash` symbol belongs to DuckStation's bundled API; select the matching API of WiiStation's pinned upstream rcheevos revision rather than assuming names from this wrapper compile unchanged. Initial start uses `rc_client_begin_load_game`; successful media callbacks retain session association and avoid rewriting the hash database from an associated swap. Unknown/failed media disables hardcore; login-required is handled separately. WiiStation must rehash the actual selected disc after ISO/PBP/subimage changes and let rc_client decide whether it belongs to the loaded game's set. [media lifecycle, lines 1160–1330](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L1160-L1330), [system hash notification, lines 4240–4245](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/system.cpp#L4240-L4245).

## HTTP, login, and pending unlocks

The server adapter sends GET or POST, supplies its user-agent header, tags requests with the achievements state's owner pointer, and uses a 60-second timeout. URL and POST text enter downloader-owned `std::string` storage. On completion it forwards the real body length/status to rc_client under the achievements mutex; cancelled operations become non-retryable client errors and other negative transport outcomes become retryable errors. Callback response storage lasts through the immediate upstream callback. The desktop downloader's WinHTTP/libcurl backends do not establish a Wii-ready TLS transport. WiiStation still needs verified HTTPS, request ownership, completion polling, cancellation, and shutdown handling. [adapter, lines 866–939](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L866-L939), [owned request creation, lines 219–235](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/util/http_downloader.cpp#L219-L235), [completion polling, lines 279–422](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/util/http_downloader.cpp#L279-L422).

Password login returns a username/token through the client. The wrapper persists an encrypted token and later attempts token login; decryption failure requests login again. Its AES-CBC key derives from username plus a machine identifier outside portable mode, with SHA256 rounds; portable mode omits the machine identifier. This is not an OS secure credential store or a ready-made Wii security design. Implement explicit remember-login semantics and a documented protection limit for removable storage. [token login, lines 697–725](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L697-L725), [password callback, lines 2117–2165](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L2117-L2165), [key/encryption, lines 2388–2536](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L2388-L2536).

Disconnected/reconnected events tell users that pending submissions are being retried or have completed; the pending count comes from `rc_client_get_pending_unlock_count`. These inspected wrapper paths demonstrate live-session retry visibility. They do not demonstrate a durable restart-safe unlock queue or authorize a session started fully offline. The local progress/hash database and badge cache should not be conflated with a submission outbox. WiiStation's offline claims must follow the upstream service rules and separate verified behavior from any future durable queue design. [events, lines 1855–1873](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L1855-L1873), [pending count, lines 2320–2327](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L2320-L2327).

## Save states and hardcore

Achievement runtime data is serialized with `rc_client_progress_size` and the sized serialization APIs. A length-prefixed optional state section can be skipped while achievements are inactive. Loading waits for pending login/game activation before restoring progress; missing data resets the runtime, and deserialization failure logs that runtime reset occurred. This is runtime state, not durable server submission state. WiiStation's existing optional WSXE sections can carry a bounded achievement blob without changing its base emulator format. Softcore loads must restore/reset this blob coherently; hardcore loads must be blocked or explicitly disable hardcore before emulation mutates. [state implementation, lines 1935–2046](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L1935-L2046).

Hardcore starts at system boot/reset, rather than silently enabling midway through play. Reset can re-enable a desired mode and resets the client runtime; deferred enablement tells the user to restart. The main state-load, undo-load, and frame-step paths ask to disable hardcore before proceeding. Its settings restriction function disables rewind and debugging, forces automatic console region and normal video timing, disallows speeds below 1×, and disables CPU underclocking below 100%; this block does not prohibit all overclocking or all visual enhancements. Changes reload cheat policy and reapply settings on the core thread. WiiStation must audit every equivalent entry point rather than only greying out one menu. [start/reset, lines 1078–1157](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L1078-L1157), [load guard, lines 2927–2944](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/system.cpp#L2927-L2944), [frame-step guard, lines 3864–3877](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/system.cpp#L3864-L3877), [undo guard, lines 5428–5442](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/system.cpp#L5428-L5442), [settings, lines 1258–1280](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/settings.cpp#L1258-L1280), [policy transition, lines 1895–1932](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L1895-L1932).

One subtlety: its reset event handler schedules a reset for RAIntegration, but otherwise ignores `RC_CLIENT_EVENT_RESET`. That behavior relies on its controlled boot/reset enablement path and must not be generalized into permission for WiiStation to ignore upstream reset requirements. The safest independent design handles reset explicitly and verifies that hardcore transitions begin from a clean emulated system. [reset event, lines 1457–1472](https://github.com/stenzek/duckstation/blob/cd024df237d46faa4c65574b101261b31267e2fd/src/core/achievements.cpp#L1457-L1472).

## Scope for the first WiiStation implementation

The reusable design lessons are a single rc_client owner, accurate raw memory, canonical selected-disc identity, frame/idle pumping, asynchronous verified HTTPS, token login, coherent softcore runtime state, and complete hardcore entry-point restrictions. DuckStation's desktop SQL caches, graphics overlays, RAIntegration loader, large UI model, and backend-specific downloader are optional architecture rather than prerequisites. Defer those and independently validate on Wii hardware. This research establishes implementation behavior at one pinned revision; it does not prove Wii performance, current service approval, every disc format's hashing coverage, or restart-safe offline submission.
